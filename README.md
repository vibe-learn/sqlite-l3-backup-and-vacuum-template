        # sqlite — Бэкап и VACUUM

        Homework-шаблон для урока **l3_backup_and_vacuum** (Бэкап и VACUUM) на платформе Vibe Learn.

        ## Что делать

        На Python (stdlib sqlite3) реализуй утилиту обслуживания базы. Функции: hot_backup(src_path, dst_path)
— горячий бэкап через Online Backup API (conn.backup), который консистентен под записью; verify(path)
— прогоняет PRAGMA integrity_check и возвращает True/'ok'; compact(path) — VACUUM, возвращает размер
файла до и после. Дополнительно демонстрируй: создай базу, вставь N строк, удали половину, покажи,
что размер файла НЕ упал, затем compact() и покажи, что упал. Тесты (на файловой базе во временной
директории): (1) hot_backup делает открываемую копию даже при параллельных вставках в src;
(2) verify на свежей базе возвращает ok; (3) compact реально уменьшает файл после массового DELETE.

## Контекст (из transfer-задачи урока)

Прод-сервис на SQLite (WAL включён), база app.db выросла до 40 ГБ. Две проблемы. (1) Команда
бэкапа в cron сейчас — `cp /data/app.db /backups/app-$(date).db`, и при тесте восстановления
одна из копий не открылась (битая). (2) После большой чистки старых данных (DELETE ~15 ГБ
строк) файл на диске остался 40 ГБ, место не вернулось. Плюс начальство просит «чтобы при
падении сервера можно было восстановить базу на любой момент».

**Вопрос:** разбери и предложи решение:
(a) почему cp-бэкап дал битую копию и чем его заменить;
(b) почему файл не сжался после DELETE и как вернуть место (с оговоркой про стоимость на 40 ГБ);
(c) какой режим auto_vacuum стоило выбрать заранее и почему его нельзя просто «включить сейчас»;
(d) чем закрыть требование «восстановление на любой момент» (PITR) и репликацию.

## Recap из урока

- Наивный `cp app.db` под записью = **торн-копия** (страницы неатомарны, изменения в `-wal` не скопированы). Безопасно — только когда никто не пишет.
- Безопасные бэкапы под нагрузкой: **`.backup` (CLI)**, **Online Backup API** (страница-за-страницей), **`VACUUM INTO 'file'`** (консистентно + дефрагментированно).
- **DELETE не возвращает место ОС** — лишь пополняет freelist. Файл сжимает только **`VACUUM`** (переписывает весь файл — дорого на большой базе). Параллель: PostgreSQL VACUUM FULL.
- `auto_vacuum`: **NONE** (дефолт, ручной VACUUM), **FULL** (авто-сжатие на коммите), **INCREMENTAL** (порциями). Режим выбирают заранее — смена на наполненной базе требует полного VACUUM.
- Durability в проде: **Litestream** (стрим WAL в S3 → continuous replication + PITR) и **LiteFS** (read-реплики между узлами). Целостность — `PRAGMA integrity_check`.

        ## Как работать

        1. Платформа Vibe Learn создаёт копию этого репо в твоём GitHub-аккаунте по клику «Начать домашку» на странице урока (через GitHub `/generate`, codecrafters-pattern).

        3. CI (`.github/workflows/ci.yml`) ставит зависимости и запускает `pytest` на каждый push. Платформа слушает результат через webhook от GitHub Actions и обновляет статус домашки на странице урока.

        ## Локальное окружение

        - Python 3.12+
        - SQLite встроена — **никакого сервера и docker-compose**. БД это один файл (`DATABASE_PATH`) или `:memory:` в тестах. Модуль `sqlite3` входит в stdlib, ставить драйвер не нужно — единственная зависимость это `pytest`.

        ## Запуск

        ```bash
        # Установить зависимости (только pytest)
        pip install -r requirements.txt

        # Прогнать тесты (бегут на :memory:-базе, ничего поднимать не нужно)
        pytest

        # Запустить main (печатает marker; замени stub на реализацию)
        python main.py

        # На файловой БД (нужно для backup/vacuum-уроков):
        DATABASE_PATH=./app.db python main.py
        ```
